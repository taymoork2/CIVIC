The real app sits in the middle. Everything else stays out of its way until you need it.

Rehearsal is a review workspace, not a dashboard. You pick a step, use the actual components with synthetic records, mark what’s wrong right on the element, and later reproduce that exact moment to check the fix. The proposal keeps the Claude Design structure (journeys left, preview center, inspector right) and changes four things that decide whether it holds up in daily review.

  1. Context becomes four chips, not six dropdowns. Persona, Permission, Condition and Display sit in one line above the preview and open a single grouped popover (a sheet on mobile). Persona, permission and data condition stay separate fields, and Condition turns amber when it isn’t Normal so a save-failure run can’t be mistaken for a normal one.
  2. Spike marking is the one signature interaction. Press P or tap Mark, and corner ticks like stage spike tape snap to whatever you point at. Choosing an element pins a note that captures the region, app state, build, design revision and full context. Reproduce restores all of that and re-marks the element.
  3. Four review lanes, stated in words. Working preview, design revision, browser verification and physical-device acceptance each have their own status, written out with an icon. A stale design shows as stale and never borrows a green check from a fixed build.
  4. The page never grows. The inspector holds one selected note with a cropped capture. The note list is two lines per note, and full screenshots are reached through Reproduce, not stacked down the page.

Challenges to the current Claude Design direction

Where I pushed back

The inspector shouldn’t be a feed

A scrolling list of full screenshots is what makes today’s page so long. The inspector here shows one selected note with a cropped capture made from the live preview. Full-frame evidence comes from Reproduce, not from images stacked down the column.

“Fixed” isn’t one status

A fix in the working preview doesn’t mean the design is current, the browser has passed, or a phone has accepted it. Device acceptance can’t be recorded until the browser has passed.

Context is part of the evidence

Every capture records the persona, permission, condition, size, appearance and text size it was made under. The reproduction link is plain text that can be copied and pasted into a ticket.

Mobile is a mode, not a column

Phones get the working preview first and four tools in the bottom bar. Sheets carry the same components as desktop, so there is one design, not a separate mobile app.

Interaction details

What Codex should copy exactly

Spike marking

  • P or Mark toggles marking. The preview edge turns spike-colored and the caption gives the instruction.
  • The pointer or keyboard focus selects the nearest named region (data-el). Ticks follow with a 150ms transform, never resizing with animated layout.
  • Click or Enter pins it. Marking ends and the composer focuses the textarea.
  • Esc exits marking without side effects.

Reproduce

  • Restores journey, step, persona, permission, condition, size, appearance and text size from the note.
  • Selects the note and re-marks the element (three short pulses, static under reduced motion).
  • Goes through the draft guard like any other context change.

Drafts and durability

  • An unsaved draft blocks any change of step, journey, context or reproduction behind a dialog. Keep editing has default focus.
  • Saved notes and synthetic records persist and are never touched by discarding.
  • A failed save keeps the text, pin and capture in place. Retry re-sends the captured state, not the current one.

Keyboard map

  • P mark · Esc exit mark or close sheet · [ ] previous / next step
  • A skip link jumps to the preview. All chips, pins and lanes are buttons with accessible names.
  • Live region announcements cover pin, save, error, reproduce and copy.
Honest risks

What this does not prove

  • Not implemented or verified. This is a design prototype. Nothing has been checked in a browser test, on a device or with assistive technology.
  • The reviewed app is a stand-in. The towel screens imitate a laundry app with synthetic data. Codex has to mount the real Laundry components in the preview slot and isolate their styles (iframe or shadow root).
  • Captures are re-rendered, not pixel screenshots. The crop clones the live preview DOM. Real evidence has to be a stored raster or a DOM snapshot pinned to a build.
  • Element targeting depends on stable region IDs. Marks rely on data-el-style annotations in the reviewed app. Without them, pins drift between builds.
  • Mapping 34 scenarios to journeys is assumed. I grouped them into 5 journeys with step lists. The real inventory may split differently.
  • Small screens are tight. A 393 preview in a 390 viewport renders at about 95% scale. A 1024 preview on a phone renders at about 36% and is effectively read-only there.
  • The system font stack renders SF only on Apple platforms. Elsewhere the hierarchy relies on weight and size alone.
